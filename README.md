> **Why the `.ows` files sit at the top level rather than in `orange/`.** Orange
> makes a stored path portable by recording it relative to the folder containing
> the workflow. It only does so when the dataset lives *inside* that folder —
> with the workflows one level down, `data/` would be a sibling, the relative
> path would be silently dropped the first time Orange rewrote it, and the files
> would revert to absolute paths that work on nobody else's machine. Keeping the
> workflows beside `data/` is what makes them portable for good.

## How the notebooks work

- Cells marked **DEMO** are worked for you. Read, run, and modify them.
- Cells marked **TASK** are yours: replace `None` with your answer.
- `checks.task("3.1", answer)` grades it immediately. It **never raises**, so a
  notebook always runs top to bottom even with tasks unattempted.

```python
kemencengan = None          # ← your answer here
checks.task("3.1", kemencengan)
# ⏳ Task 3.1: not attempted yet (assign your answer, then re-run this cell).
```

Each notebook ends with an assessed **take-home** section.

### Submitting

Restart the kernel and run everything (*Kernel → Restart Kernel and Run All
Cells*) before submitting. A notebook that only works if you run cell 14 before
cell 9 is not reproducible, and reproducibility is graded.

## Orange

Install separately — it is a desktop application, not a library:

```bash
pip install orange3          # or download the installer from orangedatamining.com
orange-canvas week03_eda.ows
```

Each workflow carries **annotation boxes on the canvas** telling you what to do,
so you can work through them without the book open. The File widgets already
point at the right dataset.

Widgets are restricted to those covered in the Orange *Introduction to Data
Science* video series, so nothing should be unfamiliar.

### Moving the folder

The workflows are **portable**. Each File widget stores its dataset twice: an
absolute path, and a path relative to the `.ows` file (`data/…`). Orange uses the
absolute one when it exists and falls back to the relative one when it does not,
so copying the whole `practicum/` folder anywhere — another machine, a USB stick,
a different drive — keeps everything working, and keeps working after Orange
re-saves the file. What must be preserved is the *layout*: the `.ows` files
beside the `data/` folder.

> If a File widget does show an error, the layout was broken. Double-click it and
> re-select the file from `practicum/data/`; everything downstream then updates.

### Widgets that ship pre-configured

Two workflows would otherwise open in a state that cannot demonstrate their own
point, so they carry settings:

- **Week 4** — the Python Script widget already contains the whole analysis (the
  sample-ratio check, the two-proportion *z*-test with a confidence interval, the
  required sample size, and the per-device segments with a Holm correction), so it
  runs as shipped. That script also lives at `orange/scripts/ab_test.py` and can be
  run on its own with `python scripts/ab_test.py`, which is how it is tested.
- **Week 5** has two parts.
  - *Part A, features:* the Feature Constructor already holds `dti`, `pti` and
    `util`; Select Columns keeps only those three; Box Plot shows `dti` by
    `default`; kNN uses k = 15 and Random Forest a fixed seed. Four learners feed
    three Test and Score widgets (raw columns / + ratios / ratios only), so the
    features are the only thing that changes. The scaled learners receive a
    Preprocess *impute → normalise → one-hot* chain through their `Preprocessor`
    input. That chain must restate the imputation and one-hot encoding: a
    preprocessor sent to a learner **replaces** the learner's defaults, so
    sending "normalise" alone makes logistic regression fail.
  - *Part B, PCA:* the Preprocess widget has *Normalize Features* enabled
    (mean 0, sd 1), and both PCA widgets have their own *Normalize variables*
    switched **off**. Orange's PCA widget normalises by default; left on, it
    would scale the "unscaled" branch too and both branches would report
    identical variance. Toggle Preprocess off to see the contrast collapse.

  Select Columns and Box Plot store their choices as *context* settings keyed
  on the input domain, so `build_workflows.py` configures a live widget and
  saves what it would save, rather than writing them by hand.

### Orange version

Developed and verified against **Orange 3.40**. A few widget classes have been
renamed across releases — the Data Table is `owtable.OWTable` now but was
`owtable.OWDataTable` in older versions, and a workflow naming the wrong one
fails to load outright. `build_workflows.py` resolves each name against your
installed Orange and falls back to the known alias, so regenerating the
workflows on an older version produces files that match it.

### Instructors: regenerating and checking

```bash
cd orange
python build_workflows.py      # regenerate all seven .ows files
python validate_workflows.py   # structural + semantic checks
```

There are three levels of checking, and they catch different things:

| Script | Checks | Caught during development |
| --- | --- | --- |
| `validate_workflows.py` | XML structure; links point at real nodes; datasets exist. With Orange importable: every widget class and **every channel name** against the live registry | `Preprocess` emits `Preprocessed Data`, not `Data`; `OWDataTable` does not exist in Orange 3.40 |
| `run_workflows.py` | **Instantiates every widget and runs the signal manager**, then asks whether the File widgets actually produced data and downstream widgets received it | That "the scheme loads" proves nothing — a workflow can load cleanly and still deliver no data |
| `run_workflows.py --moved` | Rewrites every stored absolute path to a nonexistent one, then checks the dataset is still found via `basedir` | The original workflows were **not portable**: they carried absolute paths only and would have broken on every student's machine |

```bash
python run_workflows.py            # execute all seven
python run_workflows.py week03     # just one
python run_workflows.py --moved    # simulate a relocated course folder
```

Note that `OWFile` defers its read with `QTimer.singleShot`, so "the signal
manager has nothing pending" is *not* a sufficient stopping condition — checking
only that reports a false failure before the timer has even fired.

## Instructors: rebuilding the notebooks

The notebooks are generated from percent-format sources in `_src/`, so they are
diffable in git and cannot accumulate stale outputs.

```bash
python build.py                    # rebuild all notebooks
python build.py --run              # rebuild, then execute each one to verify
python build.py --only week03      # just one
```

`--run` executes every notebook in a fresh kernel and fails loudly if any cell
raises. Run it before releasing changes to students.

To add a task, add a checker to `CHECKS` in `checks.py` and reference it from
the notebook source.

## Instructors: the teaching edition

The teaching edition is the student notebook with every TASK worked and a
commentary cell after each output explaining what the numbers say and what to
draw out of them. It is meant to be projected in class.

```bash
python build_teaching.py             # build, execute, render PDFs
python build_teaching.py --only week03
python build_teaching.py --students  # also render the blank handouts
python build_teaching.py --no-run    # build the sources only
```

| Path | What it is |
| --- | --- |
| `teaching/notes_weekNN.py` | the solutions and the commentary, keyed by **student**-notebook cell index |
| `_src_teaching/` | the merged percent-format source, editable like `_src/` |
| `notebooks/teaching/` | the executed notebooks — open these to teach from a live kernel |
| `pdf/weekNN_*_teaching.pdf` | the executed notebook, print-ready |
| `pdf/student/` | the same notebooks with no outputs, as a handout |

`_src/` is never modified, so the student notebooks and the teaching edition
cannot drift apart: a change to a source cell flows into both on the next
build. If you insert or remove a cell in `_src/`, the indices in the matching
`teaching/notes_weekNN.py` shift — the build fails loudly when an index no
longer exists, but a *shifted* index attaches the note to the wrong cell, so
re-check the affected week's notes after editing a source.

PDFs are produced by `nb2pdf.py`, which converts with `nbconvert` and
paginates with WeasyPrint. No LaTeX and no headless browser are involved.

```bash
python nb2pdf.py notebooks/teaching/week03_eda_teaching.ipynb --outdir pdf
```
